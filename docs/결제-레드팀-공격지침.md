# 결제 레드팀 공격 지침 (PAYMENT RED-TEAM PLAYBOOK)

> 이 문서는 **한 세션에게 통째로 주면 그 세션이 결제 기능을 적대적으로 깨부수는** 자립형 지침서다.
> 짝 문서 = `docs/결제-연동-핸드오프.md`(결제 플로우 설계). 이 둘을 같이 주면 공격 세션이 대상 구조를 이해하고 바로 팬다.
> 작성 근거: 아래 §참고자료(OWASP 결제 비즈니스로직 테스트 32항 · 토스 공식 문서 · 결제 레이스컨디션/멱등성 문헌) + 이 저장소 실제 코드.

---

## 0. 너의 임무 (이 문서를 받은 세션에게)

너는 지금부터 **결제 기능을 부수는 적대적 테스터(red team)** 다. 착한 QA가 아니다.
"정상 흐름이 돌아간다"를 확인하는 건 네 일이 아니다. 네 일은 **돈과 지급이 어긋나는 경로를 찾아내는 것**이다.

성공의 정의는 하나다: **결제하지 않고 물건을 얻거나, 적게 내고 물건을 얻거나, 한 번 내고 여러 번 얻거나, 남의 것을 건드리거나, 시스템이 어긋난 걸 모르게 만드는 것.** 하나라도 되면 넌 이긴 거고 그건 보고할 버그다.

접근 태도:
- **서버를 믿지 마라. 클라이언트가 보내는 모든 값은 공격자가 정한다.** 프론트 화면은 무시하고 엔드포인트에 직접 쏴라.
- **한 번 되는 걸 확인했으면 거기서 멈추지 말고 20번 동시에 쏴라.** 단일 요청은 통과하는데 동시 요청은 무너지는 게 결제의 전형이다.
- **정상 응답도 의심하라.** `{ ok: true }` 가 왔어도 DB에 지급이 두 번 박혔는지, 남의 계정에 박혔는지는 별개다. 반드시 부수효과(side effect)를 직접 확인하라.
- 막히면 각도를 바꿔라. 금액이 막히면 수량, 수량이 막히면 통화, 통화가 막히면 순서, 순서가 막히면 동시성.

## 1. 교전 규칙 (반드시 지킬 것 — 안 지키면 진짜 사고)

1. **테스트 환경/테스트 키(`test_*`)에서만.** 라이브 키(`live_*`)·실 카드·실 계좌·프로덕션 DB 대상 공격 절대 금지. 대상이 프로덕션을 가리키면 즉시 멈추고 사용자에게 물어라.
2. **파괴적 액션은 격리된 데이터에서만.** 대량 insert/삭제로 테스트 DB를 오염시킬 거면 롤백 계획이나 전용 테스트 유저를 먼저 준비하라.
3. **자동화는 레이트리밋을 존중.** 토스 테스트 환경은 **API 분당 100건 제한**이다. 동시성 공격은 짧은 버스트로, 대상 Edge Function도 마찬가지로 조심.
4. **모든 시도를 기록하라.** 무엇을 보냈고 무엇이 돌아왔고 DB가 어떻게 됐는지. 재현 안 되는 취약점은 취약점이 아니다.
5. **실제 사람/외부 서비스를 향하지 마라.** 이건 우리 앱 우리 결제에 대한 내부 강건성 테스트다.

## 2. 대상 시스템 (이 저장소 기준 사실)

- **프론트→백엔드 호출**: `src/lib/supabase.ts` 의 `callFunction(name, body, extraHeaders)`. 실제로는 그냥 `POST {SUPABASE_URL}/functions/v1/{name}` 에 헤더 `Authorization: Bearer <access_token 또는 anonKey>`, `apikey: <anonKey>`, body = JSON. **즉 공격자는 프론트를 거치지 않고 이 엔드포인트에 curl 로 직접 쏠 수 있다.** 프론트의 검증·비활성화 버튼·금액 표시는 전부 장식이다.
- **결제가 붙는 두 자리**:
  - 이북 구매: `supabase/functions/ebooks/index.ts` 의 `action:'buy'`. 현재는 데모(버튼 누르면 즉시 지급, `source:'demo'`). PG 붙으면 여기서 `paymentKey` 검증 후 지급.
  - 응시료: `src/pages/ExamApply.tsx` → (아직 미연결) 주문 저장·결제 함수. 새로 생김.
- **PG**: 국내 원화 = 토스페이먼츠 V2 표준 SDK(결제위젯). 흐름 = 클라 `requestPayment` → `successUrl?paymentKey&orderId&amount` 리다이렉트 → **서버가 `/v1/payments/confirm` 호출해야 확정**. 해외 = 엑심베이(나중).
- **보안 모델**: 잠금 테이블(`test_attempts` 등)은 RLS 미부여 = service role 전용, 채점·지급은 Edge Function에서만. 시크릿 키는 Supabase 함수 시크릿(구조상 프론트 비노출). **이 구조가 지켜지는지가 공격 1순위 점검 대상.**
- **이미 있는 방어**(우회 시도 대상): `ebook_purchases` 의 `unique(user_id, ebook_id)` + 23505를 성공으로 접는 멱등 처리. `price_paid` 는 클라가 아니라 서버가 `book.price` 로 채움.

> ⚠️ 위 "사실"은 문서 작성 시점 기준이다. 공격 전에 실제 파일을 다시 읽어 어긋나면 코드를 믿어라. 결제 연동이 진행되면 새 함수/테이블이 생기므로 대상 목록을 갱신하며 팬다.

## 4. 공격 카탈로그

각 항목: **노림수 → 재현(구체 요청) → 취약 판정 → 우리 코드에서 볼 곳 → 기대 방어**.
공격 세션은 이 목록을 위에서 아래로 훑되, 우리 코드에 실제로 존재하는 표면부터 판다.

### A. 금액·가격 조작 (→ W2)

**A1. successUrl amount 위조 (confirm에 조작값 전달)**
- 재현: 정상 결제를 1,000원으로 시작 → 리다이렉트 직전/직후 `amount` 를 `100` 으로 바꿔 서버 confirm 트리거로 전달.
- 판정: 서버가 successUrl의 amount를 그대로 confirm API에 넣으면 취약. **올바른 서버는 저장된 주문 금액과 비교 후 다를 때 confirm 거부.** (토스도 authenticated amount와 다르면 confirm 자체를 막지만, 우리가 successUrl 값을 신뢰해 지급 로직을 돌리면 그 사이에서 샌다.)
- 볼 곳: confirm 호출부. `amount` 를 요청 쿼리에서 읽는가, DB에서 읽는가.
- 방어: confirm에는 **서버 저장 금액**만 사용.

**A2. 주문 생성 시 금액을 클라가 지정**
- 재현: 주문 생성 요청 body에 `amount`/`price` 를 직접 넣어 1원짜리 주문 생성 → 정상 결제.
- 판정: 서버가 body의 금액을 저장하면 취약. **서버는 상품ID만 받아 가격을 자기가 다시 계산해야 한다.** 저장 금액과 confirm 금액이 같아도 그 저장 금액 자체가 조작됐으면 A1 방어가 무의미(조작값끼리 비교).
- 볼 곳: 주문 생성 함수가 `body.amount` 를 쓰는지 `exam_fees`/`ebooks.price` 를 다시 조회하는지.
- 방어: 금액은 **항상 서버가 product_ref로 재계산.**

**A3. 통화 스와프**
- 재현: `currency` 를 `KRW`→`USD`(또는 반대)로 바꿔 숫자값 유지. 1000 KRW 주문을 1000 "다른통화"로.
- 판정: 서버가 통화를 검증 안 하거나 환산 없이 숫자만 보면 취약.
- 방어: (통화, 금액) 쌍을 상품 정의와 정확히 대조. V2 표준은 KRW 고정이므로 KRW 외 값은 거부.

**A4. 음수·소수·정수오버플로 금액**
- 재현: 금액 `-1000`, `0`, `0.9`(KRW는 정수여야), `999999999999`, `"1000"`(문자열), `1e3`, `NaN`.
- 판정: 서버가 타입/부호/범위 검증 없이 통과시키면 취약. 음수 지급이 잔액·정산을 뒤집는지 확인.
- 방어: 정수·양수·상한 검증, 타입 강제.

**A5. 수량/개수 조작 (응시권·복수구매 생기면)**
- 재현: `quantity: -1`, `0.1`, 파라미터 중복 `quantity=5&quantity=1`(HTTP Parameter Pollution).
- 판정: 음수 수량이 총액을 깎거나, 중복 파라미터에서 서버가 더 작은 값을 채택하면 취약.

### B. 주문·소유권 (IDOR) (→ W4)

**B1. 남의 주문에 내 결제 붙이기 / 내 주문에 남의 결제 붙이기**
- 재현: 주문 생성은 유저 A로, confirm/지급 요청의 `orderId` 를 유저 B의 주문으로. 또는 다른 유저의 `paymentKey`.
- 판정: 서버가 "이 orderId가 이 인증유저 소유인가"를 확인 안 하면 취약.
- 볼 곳: confirm/지급 함수에서 `order.user_id === uid` 체크 유무.
- 방어: 모든 주문·결제 접근에 소유자 일치 강제.

**B2. 구매내역·영수증·이북열람 IDOR**
- 재현: `read`/영수증/라이브러리 액션에 남의 `ebook_id`·구매ID·주문ID를 넣어 조회.
- 판정: 소유 안 한 리소스가 반환되면 취약.
- 볼 곳: `ebooks` 함수 `read` 는 `ebook_purchases` 소유 확인 후 서명URL 발급(현재 되어 있음) — **회귀했는지 확인.**

**B3. customerKey 예측/탈취**
- 재현: `customerKey` 에 이메일·회원ID·순번 등 예측 가능한 값을 쓰는지 확인. 남의 customerKey로 결제 문맥 생성 시도.
- 판정: 토스 규격상 customerKey는 예측 가능값 금지. 예측되면 타인 결제수단·빌링 오용 위험.
- 방어: UUID 등 비예측값, 계정 귀속.

### C. 결제 흐름 우회 (→ W1)

**C1. 성공 페이지/지급 엔드포인트 강제 호출 (force-browse)**
- 재현: 결제를 아예 안 하고, 또는 실패(failUrl)로 끝난 뒤 **지급을 유발하는 엔드포인트를 직접 호출**. 예: `ebooks` `buy` 를 `paymentKey` 없이/가짜로 호출.
- 판정: confirm 성공 검증 없이 지급되면 취약(W1). **현재 데모 buy는 정확히 이 상태 — PG 붙이면 반드시 닫아야 함.**
- 방어: 지급은 **서버가 토스 confirm 200(status DONE) 을 직접 받은 뒤에만.** failUrl 파라미터로는 절대 confirm/지급 금지.

**C2. confirm 단계 건너뛰기 / 인증만으로 완료 처리**
- 재현: 인증(requestPayment)만 하고 confirm 안 한 상태에서 지급 유발. 또는 `status` 를 클라가 `DONE` 으로 주장.
- 판정: 서버가 클라 주장 상태를 믿으면 취약.
- 방어: 상태는 항상 토스 조회/confirm 응답에서만 인정.

**C3. gara-default 유사 — 무료/게스트 경로로 유료기능 취득**
- 재현: 게스트/익명 토큰으로 지급 엔드포인트 호출. 무료 레벨테스트 토큰으로 유료 CBT/이북 접근.
- 판정: 익명·비결제 유저에게 유료 산출물이 나가면 취약.

### D. 리플레이 & 멱등성 (→ W3)

**D1. 성공 콜백/지급 요청 리플레이**
- 재현: 성공한 지급 요청(같은 `paymentKey`·`orderId`)을 그대로 2~50회 재전송.
- 판정: 지급/구매/적립이 여러 번 박히면 취약(W3). 이북이 두 번, 응시권이 두 장.
- 볼 곳: 지급 테이블에 `unique(payment_id)` 또는 `unique(user_id, product)` 가 있는지. `ebook_purchases` 는 unique가 있으니 **회귀 여부 + 응시권 테이블엔 있는지** 확인.
- 방어: 지급의 유일성은 코드가 아니라 **DB unique 제약**으로. 토스 confirm엔 `Idempotency-Key`.

**D2. Idempotency-Key 오용**
- 재현: 같은 결제인데 매 재시도마다 새 Idempotency-Key. 또는 GET에 Idempotency-Key(무시됨을 이용).
- 판정: 키를 매번 갈면 토스 중복승인 방어가 리셋 → 중복 승인.
- 방어: 논리적 1결제 = 1키 고정, 15일 유효.

**D3. 웹훅 중복·순서역전**
- 재현: 같은 웹훅 이벤트를 여러 번, 또는 `DONE` 다음에 오래된 `WAITING` 을 뒤늦게 주입.
- 판정: 상태가 뒤로 돌아가거나 지급이 재실행되면 취약.
- 방어: 상태전이 멱등("이미 DONE이면 무시"), 항상 조회 API로 재검증.

### E. 레이스 컨디션 / 동시성 (→ W3, W8) — **가장 잘 터지는 구간**

**E1. 동시 confirm/지급 (double-spend)**
- 재현: **동일 orderId로 confirm/지급 요청 20~50개를 병렬로 동시 발사**(curl `&` 루프, xargs -P, 또는 서브에이전트 팬아웃). unique 제약이 걸리기 전 창을 노림.
- 판정: 지급이 2건 이상 생기거나, 유니크 없이 check-then-insert면 둘 다 통과.
- 방어: `insert ... on conflict do nothing` + unique, 또는 `select ... for update` 행잠금, 또는 원자적 RPC 하나로.

**E2. 잔액/재고 초과 (있으면)**
- 재현: 코인·응시권·쿠폰 잔액 N을 동시에 N+ 번 소진 요청 병렬.
- 판정: 잔액이 음수로 내려가면 취약(가챠 코인, 초대 보상 등도 대상).
- 볼 곳: `activity_ledger`·코인 차감 경로의 원자성.

**E3. 단일사용 토큰 동시 사용**
- 재현: 초대코드·쿠폰·응시권 토큰 하나를 동시 20회 redeem.
- 판정: 2회 이상 성공하면 취약. (초대보상은 `activity_ledger` 두 unique 인덱스가 막는 설계 — 동시성에서도 버티는지 확인.)

**E4. finalize vs 상태변경 레이스**
- 재현: confirm 진행 중에 같은 주문에 취소/환불/장바구니변경을 동시에 던짐.
- 판정: "동일 요청 20개"만 말고 **finalize와 다른 상태변경을 교차**로 쏴서 정합성 깨지는지.

### F. 웹훅 위조 (→ W1, W5)

**F1. 위조 웹훅으로 지급 유발**
- 재현: 우리 웹훅 수신 엔드포인트에 `PAYMENT_STATUS_CHANGED`/`DEPOSIT_CALLBACK` 을 **직접 위조**해 임의 orderId를 `DONE` 으로 통보.
- 판정: 서버가 웹훅 페이로드만 믿고 지급하면 취약. **일반결제 웹훅은 서명 헤더가 없다** — 그래서 페이로드를 믿으면 안 되고 **반드시 `paymentKey` 로 조회 API 재호출해 상태 확인** 후에만 반영.
- 방어: 웹훅=신호일 뿐, 진실은 조회 API. 지급 조건은 조회 결과 `DONE` + 금액 일치.

**F2. 가상계좌 입금 콜백 위조 / 입금 전 완료 처리**
- 재현: 가상계좌 발급 응답만 받고 완료로 처리되는지, `DEPOSIT_CALLBACK` 없이 입금완료를 주장.
- 판정: 발급=완료로 오인하면 취약(입금 안 하고 물건 취득).
- 방어: 발급 응답 `WAITING_FOR_DEPOSIT` 은 미완, 콜백+조회로만 완료.

### G. 환불·취소 악용 (→ W7)

**G1. 소비 후 환불**: 이북 열람/응시 완료 후 전액 환불 요청 → 산출물은 남고 돈만 회수?
**G2. 부분취소 이득**: `cancelAmount` 를 총액보다 크게, 또는 반복 부분취소로 원금 초과 환불.
**G3. 취소 후 재지급**: 취소된 결제의 orderId로 지급 재유발.
**G4. 환불 계좌 바꿔치기**: 가상계좌 환불 `refundReceiveAccount` 를 공격자 계좌로.
- 방어: 환불 정책(디지털콘텐츠 청약철회 제한·회차 기준), 취소 상태 확인 후 재지급 차단, 환불 대상 계좌 검증.

### H. 토스 특유 함정 (→ 여러 W)

**H1. TossPayments-Test-Code 헤더로 에러 강제**
- 재현: confirm 호출에 `TossPayments-Test-Code: REJECT_CARD_PAYMENT`(또는 각종 에러코드)를 넣어 **의도적으로 승인 실패/타임아웃/거절**을 유발하고, 우리 서버가 그 실패를 어떻게 처리하는지 관찰.
- 판정: confirm 실패를 **즉시 최종 실패로 단정**하면 위험 — 이미 승인/인증됐을 수 있다. 실패인데 지급하거나, 성공인데 미지급으로 방치하면 취약(W5).
- 방어: confirm 실패 시 **조회 API로 상태 재확인 후 분기.**

**H2. 결제 세션 만료(10분) 경계**
- 재현: 인증 후 10분 넘겨 confirm(`NOT_FOUND_PAYMENT_SESSION`). 만료 직전 슬립 후 발사.
- 판정: 만료 결제를 성공으로 오인하거나 주문이 pending 영구방치되면 취약.

**H3. 키/주문번호 불일치(FORBIDDEN_REQUEST)**
- 재현: confirm의 `orderId`/`paymentKey` 를 최초와 다르게, 클라키/시크릿키 미스매치.
- 판정: 이 에러를 조용히 삼키고 지급하면 취약.

**H4. orderId 포맷 악용**
- 재현: `orderId` 에 공백·비ASCII·초과길이·경로문자·중복값. (규격: 6~64자 영숫자와 `-_`.)
- 판정: 규격 밖 값이 통과하거나, orderId 충돌로 다른 주문을 덮으면 취약.

### I. 오작동·카오스 (결제 밖 상태머신 붕괴) (→ W5, W8)

**I1. confirm 성공 직후 서버 지급 저장 실패 재현**: 지급 커밋 직전에 예외/타임아웃을 주입(테스트 훅) → 돈은 나갔는데 미지급. 이걸 **자동 복구하는 경로(미완결 결제 조회 배치)가 있는가?**
**I2. 클라 이탈**: requestPayment 후 창 닫기/새로고침/뒤로가기. 주문이 pending으로 영원히 남는가, 청소되는가.
**I3. 네트워크 이중화**: confirm 요청을 보내고 응답 오기 전 재전송(D2와 결합).
**I4. 동시에 두 상품**: 이북과 응시료를 같은 유저가 동시 결제 → 지급/적립이 섞이는가.
**I5. 대사 공백**: 위 어떤 공격으로 만든 불일치를 **시스템이 스스로 발견하는가?** 토스 거래내역 vs 우리 DB 대조 쿼리가 없으면, 성공한 모든 공격은 조용히 묻힌다 = 그 자체가 취약(W5).

## 5. 자동화 — 어떻게 대량으로 패는가

**직접(단발 로직 검증)**: 각 공격을 curl/httpie 한 방으로 재현 → 응답 + DB 부수효과 확인. 금액·소유권·흐름우회는 대부분 단발로 판정된다.

**동시성(E·D·F)**: 병렬 발사가 핵심.
```bash
# 동일 orderId confirm 50발 동시 (E1) — 지급 카운트를 사후 SELECT로 확인
seq 50 | xargs -P 50 -I{} curl -s -X POST "$FN/ebooks" \
  -H "Authorization: Bearer $TOKEN" -H "apikey: $ANON" \
  -H 'content-type: application/json' \
  -d '{"action":"buy","id":"'$EBOOK'","paymentKey":"'$PK'","orderId":"'$OID'","amount":1000}' &
wait
# 판정: select count(*) from ebook_purchases where user_id=... and ebook_id=...  → 1이어야 정상
```

**서브에이전트 팬아웃(넓게 훑을 때)**: 공격 카테고리(A~I)를 병렬 에이전트에 하나씩 분배 → 각자 자기 카테고리를 끝까지 판다 → 결과를 모아 중복 제거 → 각 발견을 **다른 에이전트가 적대적으로 재검증**(진짜 재현되나, 우연 아닌가) → CONFIRMED만 리포트. (사용자가 워크플로우/멀티에이전트를 명시적으로 켰을 때만 이 방식으로 확장. 아니면 직접 순차로.)

**퍼징**: 금액·수량·통화·orderId 필드에 경계값 세트(음수/0/거대수/문자열/유니코드/중복파라미터)를 표로 돌려라.

**부수효과 검증은 필수**: 모든 자동화는 요청 성공코드가 아니라 **DB 상태 + 토스 조회 API**로 판정한다. `{ok:true}` 는 증거가 아니다.
