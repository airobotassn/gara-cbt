구글 계정 소유권 & 2FA — 조직(협회) 관점

"구글 로그인(OAuth)" 을 누구의 계정으로 두느냐, 그리고 2단계 인증(2FA)이 개인에게 종속되는 문제를 어떻게 풀지 정리한 문서.

1. 문제 — 개인 계정에 두면 "조직이 개인에게 종속"

현재 앱의 구글 로그인은 개인 구글 계정의 Google Cloud 프로젝트에 만든 OAuth 클라이언트를 쓰고 있다. 이걸 협회 계정으로 옮기려는데, 그 계정의 2FA(전화·OTP·패스키)가 결국 특정 개인의 기기에 묶이면 — 그 사람이 나가거나 연락이 안 되면 협회가 계정 통제권을 잃는다.

핵심 리스크 회사(협회) 계정의 2FA가 한 사람의 폰/기기에 묶이면, 그 계정은 사실상 그 개인에게 종속된다. 조직 자산이 한 명의 부재로 마비될 수 있다.

2. 2FA의 본질 (오해 정리)

2FA 수단은 "사람"이 아니라 "계정"에 따로 붙는다. 같은 폰·같은 OTP 앱·같은 기기로 여러 계정을 각각 등록할 수 있다.

수단사실
전화번호같은 번호를 여러 계정의 2FA에 등록 가능 (한 계정 전용 아님)
OTP 앱(Authenticator)같은 앱에 계정을 새 항목으로 추가 → 계정마다 코드가 따로
패스키같은 기기에 계정별 패스키를 따로 생성 가능

즉 "기술적으로는" 같은 기기로 회사계정 2FA도 등록할 수 있다. 하지만 그래도 결국 그 기기/사람에 의존하게 되므로 조직 종속 문제는 그대로 남는다. → 그래서 조직은 아래의 구조적 해법이 필요하다.

3. 정답 — Google Workspace 권장

개인 Gmail 을 "회사 계정"으로 쓰면 이 종속 문제는 태생적으로 생긴다. 조직용 정답은 Google Workspace(회사 도메인 계정, 예: name@협회.org) 다.

  • 관리자(Admin) 콘솔이 있어 어떤 구성원의 2FA 든 관리자가 초기화·재설정 가능
  • 종속 대상이 "한 사람 폰" 이 아니라 "관리자 역할"(조직이 통제, 슈퍼관리자 여러 명 가능)로 바뀜
  • 구성원이 나가면 관리자가 계정 회수·이관 → 조직이 항상 통제권 보유
  • OAuth 를 두는 Google Cloud 프로젝트도 Workspace 조직 소유로 둘 수 있음
요약 제대로 하려면 협회 차원에서 Workspace 도입 → 계정·2FA·소유권이 조직 관리로 들어와 개인 종속이 끊긴다.

4. 차선 — 공용 Gmail 을 써야만 한다면 대안

태생적으로 취약하지만, 종속을 여러 명에게 분산시켜 위험을 줄일 수 있다.

  • 2FA 수단을 여러 개 등록 (신뢰하는 여러 구성원의 폰·보안키)
  • 백업 코드 + 비밀번호를 협회 공용 비밀번호 관리자(1Password·Bitwarden 등)에 보관 → 한 사람이 아닌 조직이 복구권 보유
  • OTP 시드도 공용 관리자에 넣으면 누구든 코드 재생성 가능

5. OAuth / GCP 관점 (실제 핵심)

앱이 쓰는 건 Google Cloud 프로젝트 안의 OAuth 클라이언트다. 계정 종속과 별개로:

  • GCP 프로젝트에 소유자(Owner)를 여러 명 둘 수 있다 (IAM). → 한 개인에 종속 X
  • Workspace 조직 밑에 프로젝트를 두면 조직이 소유한다.
  • OAuth 클라이언트를 교체해도 기존 로그인 유저는 안 깨진다 — Supabase 가 유저를 이메일로 매칭하기 때문.

  1. 협회가 Workspace 도입 여부를 먼저 결정 (조직 계정 체계의 근본).
  2. 도입하면 → 그 도메인 계정으로 Google Cloud 프로젝트 + OAuth 클라이언트를 새로 만든다.
  3. OAuth 동의 화면에 홈페이지(https://gara-home.airobotassn.workers.dev)와 개인정보처리방침 URL(/privacy)을 넣는다. (구글이 요구)
  4. 발급된 Client ID / Secret 을 Supabase → Authentication → Providers → Google 에 교체.
