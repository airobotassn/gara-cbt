요약 Executive Summary

서버 권위(채점·잠금 데이터 service-role 전용) 설계 방향은 견고합니다. 클라이언트가 정답·타인 데이터를 직접 SELECT 할 수 없고, RLS 잠금 모델도 의도대로 동작합니다. 치명적(critical) 데이터 유출/인증우회는 발견되지 않았습니다.

다만 실제 트래픽·악용에 대한 방어가 비어 있습니다. 핵심 리스크는 ① Edge Function 레이트리밋 전무 → 익명 유저 무제한 스팸, ② 3일 1회 잠금이 경합에 취약(동시요청으로 우회), ③ 안티치트 오작동으로 정상 유저의 응시가 소진되는 3건의 high 입니다. 이 3건이 "트래픽 대비"와 "사용자 신뢰"를 직접 위협하므로 최우선 처리 대상입니다.

H1HIGH트래픽

레이트리밋 전무 — 익명 유저가 start-test/submit-test를 무제한 호출

supabase/functions/start-test/index.ts:30-37 · submit-test/index.ts:24-35
영향

3일 쿨다운(hasRecentSubmission)은 비익명 유저에게만 적용됩니다(if (!user.is_anonymous)). 익명 세션은 클라에서 signInAnonymously()로 자유롭게 생성되므로, 방문자 누구나 throttle 없이 start-test를 루프로 호출 가능합니다. 호출 1건마다 문제풀 스캔(limit 200) + test_attempts INSERT + attempt_answers 20행 벌크 INSERT가 발생하고, submit/get-result/list-attempts에도 어떤 전역 제한이 없습니다. 스크립트 한 개 또는 신규 익명 유저 급증만으로 DB 쓰기 폭주·커넥션 풀 고갈·과금 폭증으로 이어집니다.

검증

4개 함수와 _shared/lib.ts 전체에 토큰버킷·고정창·rate_limits 테이블·x-forwarded-for 처리 어디에도 없음을 확인. 함수는 service-role 클라이언트라 RLS로는 막을 수 없음. (Supabase 플랫폼의 익명가입/동시성 제한이 부분 백스톱은 됨 → critical에서 high로 하향.)

권장 조치
각 함수 본작업 전에 서버측 레이트리밋. Postgres 기반 고정창/토큰버킷을 user_id(+해시된 IP)로 키잉해 단일 SQL insert ... on conflict do update ... returning count로 원자 체크, 초과 시 429 + Retry-After. 익명 start-test는 IP당 시간당 N건으로 별도 캡. 앞단 Vercel WAF 병행 권장.
H2HIGH트래픽

쿨다운/단일진행 잠금이 경합 비안전 — 동시요청으로 3일 제한 우회 + 무제한 in-progress 생성

supabase/functions/start-test/index.ts:31-45 · _shared/lib.ts:127-144
영향

start-test는 ① 쿨다운 카운트 체크 → ② in_progress→expired UPDATE → ③ 신규 attempt INSERT 를 트랜잭션·락 없이 3개 독립 문장으로 수행합니다. 동시 호출 2건이 INSERT 전에 둘 다 카운트 체크를 통과하므로 "3일 1회"와 "단일 활성 attempt" 보장이 모두 깨집니다. 게다가 hasRecentSubmission은 status='submitted'만 세는데 start-test는 in_progress만 만들므로 두 동시 start는 애초에 서로를 막지 못합니다.

검증

schema.sql의 유일 관련 인덱스는 attempts_user_idx(비유니크). 단일 in_progress를 강제하는 부분 유니크 인덱스가 없음 확인. 모든 쓰기가 service-role이라 RLS는 직렬화·유일성 어느 쪽도 제공 못 함.

권장 조치
불변식을 DB에서 강제: create unique index uniq_inprogress on test_attempts(user_id) where status='in_progress'; + 체크·INSERT를 한 트랜잭션 RPC(SECURITY DEFINER)로 묶고 pg_advisory_xact_lock(user_id)로 직렬화하거나 같은 트랜잭션 안에서 쿨다운을 재검증.

영향

검증

권장 조치
토큰을 발급 익명 세션에 바인딩(발급 anon uid 저장 후 비교)하거나 Supabase identity-linking 사용. 최소한 토큰을 localStorage에 두지 말고 로그인 왕복 동안 메모리에만 보관.

callFunction에 타임아웃·재시도·중단 처리 없음 — 백엔드 스트레스 시 재시도 폭주
